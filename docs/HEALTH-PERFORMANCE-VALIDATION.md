# 체력 표시와 재생 비용 검증

대상: 설치된 Tempest Rising 2.0.1, 기존 `Tempest_20261024_064125_c5c1f811_1` 원본 쌍.

## 원인과 변경

기존 클라이언트 데모에서 살아 있던 GDF 보병·드론·수확기의 `GetHealth`/`GetHealthMax`는 0이고 `DefaultAttributeSet`이 없었다. 위치 보조 파일 v4에도 체력은 없다. 따라서 기존 파일에 정확한 체력을 만들어 넣지 않는다.

새 v5 보조 파일은 기존 녹화 대상에서 읽은 현재/최대 체력을 선택적 H 레코드로 저장한다. 재생은 기록된 값으로 화면 안의 살아 있는 유닛·건물에 클릭을 가로채지 않는 체력바를 표시한다. 수용·사망·화면 이탈과 HUD 숨김 시 제거한다. 실제 체력 속성을 쓰거나 공격·피해 함수를 호출하지 않는다. v1~4 읽기를 유지한다.

재생 전용 Lua 보정은 게임 스레드에서 native 객체 조회와 변환 적용을 수행한다. 초기 계측에서 후반의 후보 조사·수용 상태 조회·위치 적용 비용이 컸다. 같은 녹화 스냅샷에 대한 후보 조사를 재사용하고 수용 목록 갱신 때 무효화한다. 같은 콜백 안의 수용/사망 조회를 재사용한다. 정지한 대상에 동일 위치·회전을 반복 적용하지 않으며 주기적 갱신으로 네이티브 덮어쓰기를 복구한다. 이동 중 위치 보간, 전투 효과와 사망 연출은 생략하지 않는다. 무효화된 native 객체는 매번 제외한다.

이 계측은 CPU 측 보정 비용의 근거다. 실제 경기와 리플레이의 모든 렌더링·GPU 부하가 동일하다는 의미는 아니다.

## 실제 새 녹화

세션 `00ef16296b9444de9a6df4d8e3163da7`, 파일 `Tempest_20261024_135800_00ef1629_1`에서 건설소 4000/4000, 발전소 1100/1100, 왕조 보병 100/100·150/150과 건설 현장 증가 체력을 읽었다. 정상 메뉴 복귀로 E 트레일러를 마무리했다. 별도 재생 세션 `451f720f1ba84bffaa0321ea9d43f9ce`에서 건설소·발전소 및 건설 중 체력바를 확인하고 1→2→4배속, EOF와 프로세스 종료를 확인했다. 이후 표시 높이를 객체 경계에 맞추도록 보완했다.

최종 체력 검증 세션 `0182032369ba4d18bd4ffb8bef177fd8`에서 건물 위 체력바와 수확기 표시를 확인했다. 130.045초에 읽은 native ProgressBar 15개의 비율은 기록된 260/260 수확기, 4000/4000 건설소, 1800/1800 병영 등과 일치했다. U 숨김 시 보완 체력바 수는 0, 복원 시 다시 표시됐다. 실제 U키 네 번과 일시정지/재개, 4→2배속, EOF 및 프로세스 종료를 확인했다. 이 짧은 경기에는 체력 감소 전투 표본이 없으므로 피해·회복의 실제 교전 대조는 미검증이며 이산 값 변화는 자동 테스트 근거다. 원래 게임의 다른 UI 표시는 보완 체력바 수에 포함하지 않는다.

## 비교 방법

동일 파일, 카메라 위치 `(6139.3312747885, 22804.2, 8495.1660325139)`, 동일 배속에서 native 프레임 카운트 증가량을 실제 경과 시간으로 나눠 약 1초 간격 FPS를 측정했다. 비교 실행에는 세부 함수 프로파일러를 넣지 않았다. 초기의 함수별 계측 실행은 오버헤드가 있으므로 최종 FPS 비교에서 제외한다.

수정 전 세션: `da7364c3b7234d0d83d1628e741c904a` (v0.3.22).
1차 수정 세션: `7c341815295b42aa8743aeae49c05695`.
애니메이션 기본 정보 조회 보완 후 최종 세션: `63d7a6ff8cd44d3786d049f394bf2af3`.

수정 전 150~210초/420~480초/600~660초 4배속 평균은 99.19/71.29/40.92 FPS, 700~780초 1배속은 평균 41.44 FPS (1초 표본 범위 25.27~57.48)였다.

| 구간 | 배속 | v0.3.22 평균 FPS | 최종 평균 FPS |
| --- | --- | ---: | ---: |
| 150~210초 | 4 | 99.19 | 98.81 |
| 420~480초 | 4 | 71.29 | 84.92 |
| 600~660초 | 4 | 40.92 | 49.11 |
| 700~780초 | 1 | 41.44 | 58.91 |

실제 뷰포트는 3840×2160. 최종 1배속 구간에서 카메라가 달랐던 5개 표본은 제외했고, 남은 72개 표본 범위는 35.47~76.27 FPS였다. 제외 전 77개 평균은 57.47 FPS다. 카메라 변화가 없었던 1차 수정의 같은 구간은 56.44 FPS였다. 따라서 일관된 개선은 관측했으나 모든 구간 60FPS 목표는 미달이다. 초반은 이미 빠르고 후반의 게임 스레드 부하는 남아 있다. 임의의 효과 생략이나 그래픽 설정 저하를 적용하지 않았다.

세 비교 세션 모두 897.798초 EOF 및 프로세스 종료를 확인했다. 새 크래시 폴더는 없었다. 원본 replay SHA256은 `9C0C7F32564E7A5A8863019C66CF10FA7B82594C884DB7CC4AA5805AA3E000FF`, movement는 `B61928249378413C77FDBFF27AAAFD2B2673E741AE0F72CDE052A2B7910E8C6A`로 유지됐다.

단일 PC 표본이며 다른 앱의 병행 부하를 완전히 통제하지 않았다. 1초 평균 FPS의 최솟값은 개별 프레임의 1% low나 p99가 아니다.

## 검증 한계

149개 자동 테스트에는 기존 형식 호환, 체력 감소·회복의 이산 시점, 잘못된 체력 거부, 사망·수용·HUD 숨김, 정지 위치 적용 생략과 이동 유지, 후보 캐시 무효화, 애니메이션 속도 지속 갱신이 포함된다. 모의 호스트 테스트는 실제 게임 검증과 구분한다.

성능 비교는 체력 정보가 없는 기존 파일이다. 다수의 체력바가 동시에 표시되는 대규모 새 녹화의 장시간 성능, 실제 인터넷 상대의 모든 원격 체력 전달, 모든 기종과 모든 교전에서 60FPS 유지는 미검증이다. 기존 파일에 없는 체력은 정확히 복구할 수 없으며 새 녹화에서도 기록 클라이언트에 전달되지 않은 정보는 만들어 내지 않는다.
