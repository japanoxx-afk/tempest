# v0.3.22 사망 표시·잔해 검증

검증일: 2026-10-24. 게임 2.0.1+60808. 기준 파일은 사용자가 확인한 `Tempest_20261024_064125_c5c1f811_1.replay`와 동일 이름 `.movement`이며 길이는 897.798초다.

## 확인한 원인과 변경

9분대(556~558초)에 멈춰 조사했다. 사망 판정 대상 150개에 별도 GameplayCue 액터 128개가 연결돼 있었고 110개는 숨겨지지 않은 상태였다. 실제 PersistentLevel 유닛의 사망 비트와 해당 유닛을 소유자로 가진 `GameplayCue.RepMinimal.Status.Marked.*`, `DisabledWeapon.*` 등의 연결을 확인했다. 이 표본은 별도의 복제 유닛보다는 죽은 원래 유닛에 붙은 효과였다. 모든 화면 오브젝트의 중복 가능성을 전수 배제한 것은 아니다.

사망 보병의 `PawnDeath.bDied=true`인데도 `bDisableHUDBars=false`, `bDisableStatusEffects=false`였다. 기존 코드는 파운 본체와 직접 소유 컴포넌트를 연출 유예 후 숨겼지만 별도 풀링 상태 효과 액터는 건드리지 않았다. 따라서 본체 숨김만으로 체력바와 표시 효과 수명이 끝나지 않았다. 기록된 사망 표시와 네이티브 전투 속성의 정상적인 게임플레이 사망 처리가 동일하다고 가정할 수 없다.

수정본은 재생 중 확인한 사망 대상에만 HUD 바·상태 효과·선택 표시를 비활성화한다. 사망 대상 참조를 관리하고 무효 참조는 제거한다. 약 15번의 재생 콜백마다 상태 효과를 조사하며, **현재 소유자가 사망 대상이고 태그가 `.Status.` 계열일 때만** `K2_EndGameplayCue`로 엔진의 풀 반환 경로를 실행한다. 종료된 큐를 계속 숨기는 별도 격리 캐시는 만들지 않는다. 살아 있는 대상에 재사용된 큐와 폭발·사망 태그는 이 정리 대상이 아니다. 게임플레이 능력·효과를 제거하는 함수는 호출하지 않는다.

탱크는 Blueprint의 `ReceiveOnDeath` 표시 연출 외에 네이티브 `TedVehicle:SpawnWreck`가 전용 잔해를 만든다. 사망한 중형 탱크에서 표시 함수만 단독 호출하자 `BP_VehicleWreck_MediumTank_C`가 생성됐고 포신·분리 부품·연기·화염·소멸 곡선이 확인됐다. 기존 재생의 폭발 표시만으로 이 별도 경로가 항상 전달되는 것은 아니었다.

수정본은 잔해 메시가 설정된 차량에 대해 현재 프레임의 네이티브 처리를 기다린 뒤, 잔해 호출을 관찰하지 못한 경우 표시 전용 `SpawnWreck`를 한 번 보완한다. 직접 C++ 호출은 반영 훅을 통과하지 않을 수도 있으므로 명시적 유닛 소유자가 일치하는 기존 잔해도 검사한다. 근접 위치만으로 소유 관계를 추정하지 않는다. `Die`, `OnRep_PawnDeath`, `NetMulticast_Died`, 공격·피해 함수를 복구 목적으로 호출하지 않았다.

잔해는 파운과 다른 액터이므로 파운의 시체 정리로 끄지 않는다. 양수의 `DestroyActorDelay`는 기존 2~30초 제한 없이 원래 값을 존중한다. 이 값이 없거나 유효하지 않으면 기존 8초 대체값을 유지하며, 미확인 기종의 완벽한 수명을 보장한다는 뜻은 아니다. 잔해 자신의 물리·화염·소멸 처리는 엔진에 맡긴다.

## 항공기 범위와 복구 한계

클래스 기본 정의를 실제 설치 게임에서 읽었다.

| 기종 | 잔해 정의 |
|---|---|
| 중형 탱크 | 전용 `BP_VehicleWreck_MediumTank`, 전용 잔해 메시 |
| 콘도르 | 전용 `BP_VehicleWreck_Condor`, 구성용 Plane 메시와 별도 동체 구성 |
| 전투 드론·스텔스 전투 드론 | 기본 잔해 클래스 참조는 있으나 `WreckMesh` 없음 |

메시가 없는 드론에 임의의 탱크 잔해나 추락 연출을 대체하지 않았다. 콘도르 전용 잔해 프리팹을 재생 세계에 별도로 표시하는 시험에서 동체·꼬리 화염과 메시를 확인했다. 이 시험은 임의 위치에서 프리팹만 생성한 표시 시험이며 **기록된 항공기 사망 재현이 아니다**. 일시정지 중 수집된 위치 표본으로 추락 속도를 주장하지 않는다. 콘도르의 실제 사망 → 충돌 → 소멸 전 과정, 다른 항공기 기종 및 모든 피해 유형은 미검증이다.

원본 경기의 동시 촬영 영상이나 실행 상태는 없으므로 실제 경기와 동일 장면의 영상 대조는 하지 못했다. 기록 파일에서 원래 잔해의 모든 물리 궤적·충격량·무작위 분리 상태를 복원한 것은 아니다. 게임의 현재 기종 정의를 이용해 표시 경로를 복구하며, 정확히 동일한 물리 결과는 보장하지 않는다. 이번 변경으로 녹화 형식이나 기록 이벤트는 추가하지 않았다.

## 실제 재생 검증

- 최초 기존 버전 조사: 세션 `5e2132d11d35409787754e22131b425e`, 9분대 잔존 확인. 사망 대상 소유 상태 큐 128개를 엔진 종료 경로로 반환한 뒤 연결된 큐가 0개가 됨을 확인했다.
- 초기 후보 계측 실행 `e11660da922b477c8cc128870c661fef`는 약 369.5초에서 UE4SS 내부 접근 위반으로 중단됐다. 진단용 중복 네이티브 훅과 추가 물리 조회를 제거한 이후 같은 지점에서 재현되지 않았으나 정확한 원인을 확정하지는 못했다. 이 실패 실행은 최종 성능 비교에서 제외했다.
- 후보 `9863faaf106a4e46862c03db358d17ac`: 처음부터 끝까지 완료. 4배속, 이후 1·2배속, F8 일시정지·재개, U키 4회, 미니맵으로 카메라 이동·복귀를 실제 조작했다. 9분대 정리 뒤 사망 대상 상태 효과가 누적되는 모습은 사라졌고 600초 표본의 연결된 큐·HUD 허용 대상은 0개였다. 탱크·험비의 전용 잔해 생성 로그 47건을 수집했다. 이는 모든 잔해를 계속 유지했다는 뜻이 아니다.
- 최종 코드 `33c3724b23f84ded86d37d185a8045b3`: 4배속으로 802초까지 비교 측정, 일시정지·재개 후 1배속으로 파일 끝과 자동 프로세스 종료 확인. 마지막 800초 이후의 별도 콘도르 프리팹 표시는 성능 비교 구간에서 제외했다.
- 최종 코드에서 782초 표본의 사망 대상 상태 큐와 HUD 허용 대상은 0개였다. 723초 전투 직후에는 반환 대기 큐가 10개였으나 다음 안정 표본에서는 0개였다. 모든 효과가 사망과 같은 프레임에 즉시 사라진다고 주장하지 않는다.
- `FindAllOf`가 반환한 잔해 수 31개를 802초에 개별 유효성으로 검사하면 실제 유효 잔해는 0개였다. UObject 등록부·GC 대기 수와 현재 활성 액터 수를 혼동하면 안 된다. 탱크 잔해가 영구히 누적된다는 근거로 이 원시 개수를 쓰지 않았다.
- 최종 두 완료 실행에서 추가 크래시가 발생하지 않았다. 앞의 계측 크래시 기록은 삭제하지 않았다.

2배속과 U 반복·카메라 복귀는 같은 핵심 표시 수정이 들어간 후보 실행에서 확인했으며, 최종 참조 관리·중복 방지 보강 후 동일 조합을 전부 다시 실행한 것은 아니다. 새 온라인 경기와 장시간 반복 재생은 미검증이다.

## 성능 측정

최종 비교는 기존 v0.3.21 세션 `1608c829c9a34c29ae626b562ac248a5`와 최종 코드 세션 `33c3724b23f84ded86d37d185a8045b3`다. 같은 파일, 4배속, 고정 카메라 파운 위치 `(353.6,22804.2,1600)`를 유지했다. 네이티브 프레임 카운터 / 실제 시간 차이를 약 1초마다 표본 수집했다. 프레임 시간은 각 1초 FPS의 역수 평균이며 프레임별 p95/p99나 최대 멈춤 시간이 아니다.

| 기록 시간 | 전/후 표본 수 | 평균 FPS 전 → 후 | 평균 프레임 시간 전 → 후 |
|---|---:|---:|---:|
| 150~210초 | 15 / 15 | 93.20 → 97.95 | 10.73 → 10.21ms |
| 420~480초 | 14 / 14 | 69.21 → 81.60 | 14.58 → 12.42ms |
| 720~780초 | 14 / 14 | 39.89 → 41.64 | 25.99 → 25.05ms |

782초 근처 기존/수정 표본의 사망 대상 연결 큐는 345/0, HUD 허용 대상은 316/0이었다. 원시 Actor는 5005/4715, FXSystemComponent는 5688/5531, AudioComponent는 1002/1039였다. 정상 잔해 복구와 전투·풀·GC가 함께 영향을 주므로 오디오 개수 감소나 누수 해결을 주장하지 않는다.

표시 정리 루틴의 캐시 갱신 호출은 마지막 계측에서 540회, `os.clock` 기준 평균 약 3.19ms, 관찰 최대 19ms였다. 이는 실제 전체 프레임 시간이 아니며, 대량 효과 반환 순간의 비용이 남아 있음을 뜻한다. 매 프레임 전체 오브젝트 검색은 하지 않지만, 이 구현만으로 모든 주기적 멈춤이 없어졌다고 주장하지 않는다.

초기 후보와의 첫 비교에서는 FPS가 오히려 낮은 구간도 있었다. 다른 게임 프로그램이 병행 실행된 단일 PC의 표본이며 GPU 부하·GC가 실험실처럼 통제되지 않았다. 최종 비교에서 후반 약 4.4% 상승을 관찰했지만 보장 수치나 상태 큐만의 단독 인과 효과로 해석하지 않는다. 후반 프레임 저하는 남아 있다. 정상 이동·공격·애니메이션·전투 이벤트를 성능을 위해 생략하지 않았다.

## 회귀 검사와 파일 보존
